# Design from scratch

1. Understand the primary audience, task, business outcome, content, devices, and constraints. State missing assumptions. Define a success condition such as “A visitor can identify who this product serves and find the trial entry point.”
2. Map entry → task → decision → completion → recovery. Include loading, empty, error, success, disabled, and partial-progress states where relevant. Arrange navigation around user tasks and meaningful labels, not internal team names.
3. Select principles from the symptom table in SKILL.md. For a SaaS page, Jakob may support familiar navigation, Proximity may group benefit and proof, and Von Restorff may clarify the primary action. Selection follows need, not this example.
4. Draft hierarchy with real content: useful title, readable explanation, task-based sections, clear action labels. Reuse available typography, spacing, and component tokens. Establish desktop, tablet, and mobile behavior; choose type size/line-height for content and context rather than claiming a universal law-derived scale.
5. Implement the smallest coherent flow. Use honest placeholders if real claims or integrations are unavailable; never fabricate testimonials, research, or working backend behavior. Keep optional detail discoverable.
6. Validate the declared task and relevant checklist criteria. Report functional versus illustrative behavior. If only a prototype is possible, identify what would need integration or user testing.

Deliver the requested artifact, a few decision explanations, verification evidence, and unresolved assumptions. Do not substitute a lecture for implementation.
